## 1. Privacy summary

Tiny holds very little personal data: an email address, login codes and a few logs. We collect nothing we cannot justify, and we store no passwords. Consent works in two steps. The app owner chooses to invite a person, and that person sees a one-line notice on the login page before a code is sent: "Tiny Cloud will store your email address to sign you in and to check that you were invited."

| Data item | Source | Purpose | Consent | Storage | Access | Retention |
| --- | --- | --- | --- | --- | --- | --- |
| Viewer email | Owner's invite; viewer types it at login | Check the invite, send the login code, tell the app who is viewing | Owner invites; viewer sees the login-page notice | Platform database on our server | Server only | Deleted 30 days after the last invite to that email is removed |
| Login code (6 digits) | Generated by the server | Prove the viewer owns the email | Part of login | Stored as a hash in the platform database | Server only | Deleted when used or after 10 minutes |
| Session cookie | Created at login | Keep the viewer logged in | Part of login | Hash in the platform database; cookie is HttpOnly and Secure | Server only | Expires after 30 days or at logout |
| Owner email and deploy token | Owner runs `tiny login` | Identify the owner and allow deploys | Owner signs up on purpose | Token stored as a hash in the platform database | Server only | Token expires after 90 days; deleted with the owner's account |
| Invite record (owner, viewer, app) | Owner's invite command | Decide who may open each app | Owner action | Platform database | Server only | Until the owner revokes it or deletes the app |
| App code and built app | Owner's upload | Run the app | Owner uploads on purpose | Server disk | Build and run parts only | Deleted when the owner deletes the app |
| App saved data (for example poll votes) | The running app | The app's own job | Owner's responsibility; owners should tell their users | One data file per app, visible only to that app | That app only | Deleted when the owner deletes the app |
| Secret keys set by the owner | `tiny env set` | Give the app its keys | Owner action | Encrypted in the platform database | Server only | Deleted when the owner deletes the app |
| Request logs (app, time, result, viewer IP) | Router | Fix problems and limit abuse | Covered by the login-page notice | Server disk | The two team members | Deleted after 14 days |
| Email delivery record | Resend, our email service | Deliver login codes | Part of login | Held by Resend | Resend and the team | Kept by Resend for 30 days on its free plan, and deleted within 90 days after we close our account |

**When the project ends:** we give owners 14 days of notice, then delete the server, its disk and its backups, and close the Resend and domain accounts.

**Fields we removed because we could not justify them:** viewer name and phone number, any password, analytics or tracking cookies, and long-term storage of IP addresses.

## 2. Security summary

We addressed the 3 commons gaps by name.

- **Default credentials.** There are none. The database password and the master key for secrets are random values set when the server is installed, and the first owner token is created at setup and shown once. The Docker control socket is never given to any app.
- **Unauthenticated endpoints.** Every control endpoint needs a deploy token. Every app request goes through the router, which checks for a valid login and an invite before it passes anything on. The only public pages are the login page, the code request and a health check that returns only "ok." We test this with AC-02.4 and AC-02.5.
- **Secrets in source control.** Secrets live only in server environment variables and in the encrypted secrets table. `.env` files are in `.gitignore`. No key is written into code, built apps or logs.

| Item | What we use |
| --- | --- |
| How people log in | Emailed one-time 6-digit code. No passwords. |
| Code lifetime and tries | 10 minutes; after 5 wrong tries the code stops working |
| Session lifetime | 30 days, in a HttpOnly, Secure, SameSite=Lax cookie |
| Deploy token lifetime | 90 days |
| Where secrets live | Encrypted column in the platform database. One master key sits in the server's environment, not in the database or the repo. |
| HTTPS | Caddy with a wildcard certificate for our domain; plain HTTP redirects to HTTPS |
| Rate limiting | Code requests: 5 per email per hour and 20 per IP address per hour; wrong codes: 5 per code |
| Identity header | The router removes any identity header a client sends, then sets its own |

**Git history search:** we searched the full history of the team repository with gitleaks on November 11th, 2026. Result: 0 findings across 15 commits.

**Self-audit questions and our answers:**

| Question | Answer |
| --- | --- |
| Are there any default or shared passwords? | No |
| Does every endpoint need a login, or is it deliberately public? | Every one needs a login except the login page, the code request and the health check |
| Are any secrets in the repo or its history? | No |
| Is all traffic encrypted? | Yes, HTTPS only |
| Can one app reach another app or the platform database? | No. Tests: AC-05.1 and the isolation test suite |
| Is user input limited and checked? | Yes: the rate limits above, and the router and control API reject malformed requests |
| What do we still not protect against? | A determined attacker who breaks out of a container. Docker is not a strong wall, so we only run apps for people we know. |
